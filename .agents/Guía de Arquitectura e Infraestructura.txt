Guía de Arquitectura e Infraestructura - Proyecto Bazaar
Visión General del Proyecto
Bazaar es un marketplace (e-commerce) diseñado bajo una arquitectura de microservicios. Este documento centraliza las decisiones técnicas, la configuración de infraestructura y las estrategias de despliegue adoptadas por el equipo para cumplir con los requerimientos funcionales y no funcionales (Red Lines) del Trabajo Práctico, apuntando inicialmente al Checkpoint 1.

1. Stack Tecnológico Base
Cloud Provider: DigitalOcean (DOKS - DigitalOcean Kubernetes). Elegido por su facilidad de uso y la disponibilidad de créditos estudiantiles.

Lenguaje y Framework (Backend): Los utilizados en el repositorio.

Bases de Datos: PostgreSQL (desplegadas dentro del clúster).

2. Decisiones de Arquitectura e Infraestructura
2.1. Gestión de Bases de Datos
Decisión: Las bases de datos se alojan dentro del clúster de Kubernetes (mediante Pods/Deployments o StatefulSets) en lugar de utilizar servicios gestionados (Managed DBs).

Justificación: Permite cumplir económicamente con el Red Line que exige que cada microservicio tenga su propia base de datos independiente y aislada. Además, fomenta el aprendizaje profundo sobre volúmenes persistentes en K8s.

2.2. Entornos y Namespaces
Decisión: Todos los microservicios, bases de datos y el API Gateway convivirán en un único namespace llamado bazaar-dev.

Justificación: Facilita la visibilidad integral del sistema para demostraciones, simplifica el ruteo interno (DNS) para el API Gateway y mantiene el orden frente al namespace default.

2.3. Plantilla Base (Golden Path)
Se desarrolló un "Template de Microservicio" estandarizado que incluye:

Estructura de directorios en capas (Router -> Service -> Model).

Endpoints obligatorios de observabilidad: /livez (liveness) y /readyz (readiness, con chequeo de conexión a BD).

Configuración completa de Dockerfile y manifiestos de Kubernetes (deployment.yaml, service.yaml, secret.yaml).

Límites de Recursos: Todos los deployment.yaml deben definir Requests y Limits de CPU y Memoria para garantizar la disponibilidad del clúster y evitar que un servicio sature el nodo.

2.4. Estrategia de Ahorro de Costos
Dado que DigitalOcean no permite escalar el Node Pool a 0, al finalizar las jornadas de desarrollo se ejecutará el comando kubectl scale deployment --all --replicas=0 -n bazaar-dev para apagar los microservicios, liberar recursos y asegurar que los créditos duren todo el cuatrimestre.

3. Integración y Despliegue Continuo (CI/CD)
El proyecto utiliza GitHub Actions para automatizar todo el ciclo de vida del código, cumpliendo con el Red Line de automatización de componentes.

Flujo del Pipeline (deploy.yml)
Análisis Estático y Seguridad (SAST): Ejecución de linters (ruff) y escaneo de vulnerabilidades (bandit).

Testing Unitario/Integración: Ejecución de pruebas usando un contenedor efímero de PostgreSQL levantado vía docker compose.

Construcción y Registro (CI): Si los tests pasan, se construye la imagen Docker y se publica en GitHub Container Registry (GHCR), etiquetándola unívocamente con el SHA del commit (github.sha).

Despliegue Declarativo (CD): * El runner de GitHub se autentica en DigitalOcean.

Se utiliza envsubst para inyectar la nueva etiqueta de la imagen y los secretos en los archivos .yaml de la carpeta /k8s.

Se aplica la configuración en el clúster usando kubectl apply -n bazaar-dev.

4. Seguridad y Gestión de Secretos (Red Lines)
Para cumplir estrictamente con la prohibición de subir secretos al código fuente o al historial de Git, se implementó la siguiente estrategia:

Secretos de la Aplicación (Ej. Credenciales de BD): * Los archivos secret.yaml en el repositorio son meras plantillas que utilizan variables de entorno ($DB_PASSWORD).

Los valores reales se almacenan en GitHub Secrets.

Durante el despliegue, GitHub Actions inyecta los valores en el YAML y Kubernetes los convierte a Base64 nativamente usando la propiedad stringData.

Acceso al Registry Privado (GHCR):

Se generó un Token de GitHub (Fine-grained o Classic con alcance read:packages) con autorización para la Organización.

Este token se inyectó manualmente en el clúster mediante la terminal creando un imagePullSecret.

Los deployment.yaml referencian este secreto para poder descargar las imágenes de forma segura.
